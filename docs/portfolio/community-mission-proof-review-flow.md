# 공동미션 인증 구조를 단계형 제출에서 검수 가능한 승인 흐름으로 확장

## 1. 문제 상황

공동미션은 처음에 "사용자가 필요한 인증 단계를 모두 제출하면 완료할 수 있는 구조"로 구현했습니다.

이 구조는 다회차 인증을 저장하는 데는 적합했지만, 실제 운영 흐름과는 아직 차이가 있었습니다.

- 사용자는 1일차, 4일차, 7일차처럼 여러 차례 인증을 제출할 수 있어야 했습니다.
- 관리자는 각 인증 제출을 보고 승인 또는 반려할 수 있어야 했습니다.
- 사용자는 단순 제출이 아니라 "모든 인증 단계가 승인된 뒤"에만 공동미션을 완료할 수 있어야 했습니다.

즉, 공동미션은 단순한 파일 업로드 API가 아니라

- 단계별 인증 제출 구조
- 관리자 검수 상태
- 승인 기준 완료 조건

을 함께 가져야 하는 기능이었습니다.

이 과정에서 다음 질문을 함께 풀어야 했습니다.

- 공동미션 인증은 어떤 단위로 저장해야 수정과 검수가 쉬운가
- 반려된 인증은 새 row를 만들어야 하는가, 기존 제출을 다시 제출해야 하는가
- 완료 조건은 제출 개수 기준인가, 승인 개수 기준인가
- 사용자 조회 화면과 관리자 검수 화면이 같은 데이터를 일관되게 볼 수 있는가

## 2. 왜 문제였는가

공동미션은 일반 미션과 닮아 보이지만, 구조적으로는 더 복잡했습니다.

- 일반 미션은 한 번 제출하고 한 번 검수하면 끝나는 흐름에 가깝습니다.
- 공동미션은 한 미션 안에 여러 인증 단계가 있고, 각 단계마다 이미지 수도 다를 수 있습니다.
- 일부 단계만 제출되었거나, 제출은 다 되었지만 승인되지 않은 상태도 구분해야 합니다.

초기 구조를 그대로 두면 다음 문제가 생길 수 있었습니다.

- 제출만 완료되면 공동미션 완료가 가능해져, 검수 흐름이 사실상 무력화될 수 있습니다.
- 반려된 인증을 어떻게 다시 처리할지 기준이 없어 상태 관리가 꼬일 수 있습니다.
- 사용자 화면에서는 "제출 완료"로 보이는데 실제 완료는 불가능한 상태가 생길 수 있습니다.
- 관리자 API 없이 공동미션 검수 로직을 나중에 붙이면 제출 구조를 다시 뒤집어야 할 수 있습니다.

즉, 이번 작업의 핵심은 "단계형 인증 제출 구조"를 "검수 가능한 상태 흐름"으로 확장하는 것이었습니다.

## 3. 해결 방식

이번에는 공동미션 인증을 `proof` 단위로 관리하고, 그 위에 검수 상태를 올리는 방식으로 구조를 확장했습니다.

### 적용 방식

- `community_mission_proofs`에 `status`, `reviewed_at` 컬럼을 추가했습니다.
- 검수 상태는 `PENDING`, `APPROVED`, `REJECTED` 세 가지로 관리했습니다.
- 공동미션 인증 제출은 `proof requirement` 단위로 저장되도록 유지했습니다.
- 반려된 인증은 새 row를 만드는 대신, 같은 proof를 `REJECTED -> PENDING`으로 재제출하도록 구성했습니다.
- 공동미션 완료 조건은 `모든 인증 단계 제출 완료`가 아니라 `모든 인증 단계 승인 완료`로 변경했습니다.
- 사용자 공동미션 상세 조회 응답에 제출 여부뿐 아니라 검수 상태, 검수 시각까지 포함했습니다.
- 관리자 전용 공동미션 검수 대기 목록 조회 API와 승인/반려 처리 API를 추가했습니다.

즉, 구조를 다시 만들기보다 기존 단계형 제출 구조 위에 "검수 상태"와 "승인 기준 완료 조건"을 얹는 방식으로 확장했습니다.

## 4. 왜 이 방식을 선택했는가

### 선택 이유

- 공동미션은 여러 번 인증을 제출하는 구조라, 인증 자체를 한 덩어리 completion으로 묶는 것보다 requirement별 proof로 분리하는 편이 자연스러웠습니다.
- 검수 상태는 proof 단위에 있어야 어느 단계가 반려되었는지, 어느 단계가 아직 대기 중인지 명확하게 표현할 수 있습니다.
- 반려 시 새 row를 만드는 방식보다 기존 proof를 재제출하는 방식이 상태 추적과 조회 응답을 단순하게 유지할 수 있습니다.
- 완료 조건을 제출 기준이 아니라 승인 기준으로 바꿔야 실제 운영 검수 흐름과 맞았습니다.
- 사용자 화면과 관리자 검수 화면이 같은 proof 데이터를 바라보도록 해야 이후 유지보수가 쉬워집니다.

### 고려했던 다른 방법

#### 1) 제출만 완료되면 공동미션 완료 가능하도록 유지

가장 구현은 단순하지만, 관리자 검수의 의미가 약해집니다.
공동미션처럼 여러 사용자의 성취가 누적되는 기능에서는 잘못된 제출이 전체 진행률에 영향을 줄 수 있어 적합하지 않았습니다.

#### 2) 반려 시 새 proof row를 다시 생성

이 방식은 이력은 더 명확할 수 있지만, 같은 requirement에 대해 어떤 제출이 현재 유효한지 판단하는 로직이 복잡해집니다.
현재 단계에서는 하나의 requirement에 대해 하나의 현재 제출만 유지하는 구조가 더 단순하고 실용적이었습니다.

#### 3) 공동미션도 일반 미션처럼 completion 중심 검수 구조로 통합

공동미션은 한 미션 안에 여러 인증 단계가 있다는 점이 다릅니다.
그래서 미션 completion 하나에 검수 상태를 다 얹는 방식보다, proof 단위 검수가 확장성 측면에서 더 적합했습니다.

## 5. 구현 중 중요했던 포인트

### 1) 제출 구조와 검수 구조를 따로 뒤엎지 않은 점

이미 공동미션은 `proof requirement`와 `proof images`로 단계형 인증 구조가 잡혀 있었습니다.

이번에는 그 구조를 버리지 않고,

- `proof`에 검수 상태 추가
- 관리자 API 추가
- 완료 조건 변경

만으로 확장했습니다.

이렇게 해야 이전 구현을 낭비하지 않고, 기능 확장도 자연스럽게 이어질 수 있었습니다.

### 2) 완료 조건을 승인 기준으로 바꾼 점

이전에는 `제출된 proof 수 == 필수 requirement 수`면 완료 가능했습니다.

하지만 검수 흐름이 들어오면 이 조건은 충분하지 않습니다.

예를 들어:

- 3개 단계 모두 제출 완료
- 그중 1개는 반려

인 상태라면 사용자는 아직 공동미션을 완료하면 안 됩니다.

그래서 이번에는:

- 제출 개수는 `submittedProofCount`
- 승인 개수는 `approvedProofCount`
- 완료 가능 여부는 `approvedProofCount == requiredProofCount`

로 역할을 분리했습니다.

### 3) 반려 후 재제출을 기존 proof 갱신으로 처리한 점

반려된 인증은 사용자 입장에서 "같은 단계 인증을 다시 제출하는 것"에 가깝습니다.

그래서 이번에는:

- `REJECTED` 상태의 proof만 재제출 가능
- 재제출 시 `status = PENDING`
- `reviewedAt = null`
- 이미지 목록 교체

로 처리했습니다.

이 방식은 현재 유효한 제출이 무엇인지 한눈에 알 수 있고, requirement별 상태를 단순하게 유지할 수 있다는 장점이 있었습니다.

### 4) 사용자 조회 응답과 관리자 검수 응답이 같은 상태 모델을 보게 한 점

사용자 화면에서는:

- 제출 여부
- 검수 상태
- 검수 시각
- 완료 가능 여부

가 필요하고,

관리자 화면에서는:

- 검수 대기 목록
- 어떤 유저가 어떤 단계를 제출했는지
- 제출 이미지 목록

이 필요합니다.

둘이 서로 다른 기준을 보면 금방 어긋날 수 있어서, 이번에는 둘 다 `CommunityMissionProof`를 기준으로 상태를 읽도록 맞췄습니다.

## 6. 검증 방법

### 공동미션 인증 제출 테스트

- 공동미션 인증 단계를 정상 제출할 수 있는지 확인했습니다.
- 필수 이미지 수와 다르면 제출되지 않는지 확인했습니다.
- 반려된 인증은 같은 requirement에 대해 다시 제출할 수 있는지 확인했습니다.

### 공동미션 완료 테스트

- 필수 인증 단계 수보다 제출 수가 부족하면 완료할 수 없는지 확인했습니다.
- 제출은 모두 되었지만 승인 수가 부족하면 완료할 수 없는지 확인했습니다.
- 모든 단계가 승인된 경우에만 완료 흐름이 진행되는지 확인했습니다.

### 공동미션 조회 테스트

- 목록 조회에서 `submittedProofCount`, `approvedProofCount`, `readyToComplete`가 함께 계산되는지 확인했습니다.
- 상세 조회에서 proof별 `reviewStatus`, `reviewedAt`이 응답에 포함되는지 확인했습니다.

### 관리자 검수 테스트

- 검수 대기 공동미션 인증 목록을 조회할 수 있는지 확인했습니다.
- 관리자가 `APPROVED`, `REJECTED` 상태로 검수할 수 있는지 확인했습니다.
- 이미 검수된 인증은 다시 검수할 수 없는지 확인했습니다.

### 실행 테스트

- `./gradlew test --tests 'com.zerost.api.communitymission.*'`

## 7. 이번 작업으로 해결한 것

- 공동미션 인증을 단계형 제출 구조로 저장할 수 있게 만들었습니다.
- 그 제출 구조 위에 관리자 검수 상태를 얹어 실제 운영 흐름과 연결했습니다.
- 공동미션 완료 조건을 단순 제출 기준이 아니라 승인 기준으로 바꿔 정합성을 높였습니다.
- 반려된 인증을 자연스럽게 재제출할 수 있는 흐름까지 닫았습니다.
- 사용자 조회 화면과 관리자 검수 화면이 같은 상태 모델을 바라보도록 정리했습니다.
- 배포를 막을 수 있던 Flyway 제약조건명 길이 문제도 함께 해결했습니다.

즉, 이번 작업은 "공동미션 인증 업로드 API를 만들었다" 수준이 아니라,
"다회차 인증이 필요한 공동미션을 검수 가능한 상태머신으로 확장하고, 사용자 완료 조건까지 일관되게 연결한 작업"이라고 정리할 수 있습니다.
