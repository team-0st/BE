# 일일/주간 노출 정책을 저장형 편성 구조로 분리한 설계

## 1. 문제 상황

이번 요구사항에서는 단순 조회 API를 넘어서, 화면에 노출되는 콘텐츠 자체가 정책을 가져야 했습니다.

- 오늘의 미션은 일반 미션 3개와 특별 미션 1개가 보여야 했습니다.
- 이번 주 레시피는 일반 레시피 중 1개만 선택되어 한 주 동안 고정 노출되어야 했습니다.
- 입문 레시피는 별도 섹션으로 항상 고정 노출되어야 했습니다.
- 히든 레시피는 목록에는 보이되, 상세 조합은 숨겨진 상태를 유지해야 했습니다.

즉, 요구사항의 핵심은 "조회할 때 랜덤으로 하나 고른다"가 아니라, `일정 기간 동안 고정되는 노출 정책`을 어떻게 서버 구조로 표현할 것인가였습니다.

## 2. 왜 문제였는가

이 문제를 단순 랜덤 조회로 처리하면 다음 문제가 생깁니다.

- 사용자가 앱에 다시 들어올 때마다 오늘의 미션 구성이 바뀔 수 있습니다.
- 이번 주 레시피가 요청 시점마다 달라지면 "이번 주"라는 개념이 무너집니다.
- 프론트 화면은 섹션형 구조를 기대하는데, 백엔드가 단순 목록만 주면 화면 조립 책임이 커집니다.
- 나중에 운영 정책을 바꾸거나 관리 도구를 붙일 때, 노출 상태를 추적할 기준이 사라집니다.

즉, 이 기능은 단순 조회 기능이 아니라 `콘텐츠 노출을 시간 단위 정책으로 고정하는 문제`에 가까웠습니다.

## 3. 해결 방식

이번에는 랜덤 결과를 즉석 계산으로만 소비하지 않고, 선택 결과를 저장해서 재사용하는 구조로 바꿨습니다.

### 적용 방식

- 레시피는 `is_intro` 컬럼을 추가해 입문 레시피 여부를 명시적으로 구분했습니다.
- 이번 주 레시피는 `weekly_recipe_selections` 테이블을 별도로 두어, 주차 시작일과 함께 선택 결과를 저장하도록 구성했습니다.
- 미션은 `mission_category`를 추가해 일반 미션과 특별 미션을 분리했습니다.
- 오늘의 미션은 `daily_mission_selections` 테이블을 두어 날짜별 선택 결과와 표시 순서를 저장하도록 구성했습니다.
- 조회 시에는 "이미 선택된 데이터가 있으면 재사용하고, 없으면 최초 한 번 생성"하는 방식으로 동작하게 했습니다.
- 레시피 API는 `입문 레시피 / 이번 주 레시피 / 히든 레시피` 섹션형 응답으로 재구성했습니다.
- 미션 API도 `일반 미션 목록 / 특별 미션 1개` 구조로 응답하도록 바꿨습니다.

즉, 콘텐츠를 매번 뽑는 구조가 아니라 `일간/주간 편성 결과를 저장하고 조회하는 구조`로 전환했습니다.

## 4. 왜 이 방식을 선택했는가

### 선택 이유

- 일일/주간 고정 정책은 요청 시 랜덤보다 저장형 편성이 더 자연스럽습니다.
- 스케줄러를 먼저 붙이지 않아도, 최초 요청 시 생성하는 방식으로 정책을 충분히 만족할 수 있습니다.
- 운영 정책이 바뀌거나 관리 화면이 필요해질 때도, 이미 편성 테이블이 있으면 확장하기 쉽습니다.
- 프론트가 기대하는 화면 구조에 맞는 응답을 주면 클라이언트 조립 부담을 줄일 수 있습니다.

### 고려했던 다른 방법

#### 1) 요청마다 랜덤 선택

구현은 단순하지만 오늘의 미션과 이번 주 레시피가 고정되지 않습니다.
정책 요구사항과 직접 충돌합니다.

#### 2) 배치/스케줄러를 먼저 도입

운영 환경에서는 좋은 선택일 수 있지만, 현재 단계에서는 스케줄러 장애나 실행 시점 관리까지 같이 가져가야 합니다.
이번 작업에서는 구조를 먼저 안정화하고, 생성 시점은 단순한 방식으로 두는 편이 범위 관리에 더 적절했습니다.

#### 3) 레시피에 `is_weekly` 같은 플래그만 두고 직접 토글

입문 레시피처럼 고정 속성은 플래그로 표현할 수 있지만, "매주 바뀌는 선택 결과"는 별도 이력성 구조가 더 적합했습니다.
그래서 입문 레시피는 컬럼, 이번 주 레시피는 선택 테이블로 역할을 나눴습니다.

## 5. 구현 중 중요했던 포인트

### 1) 속성과 선택 결과를 분리한 점

입문 레시피는 변하지 않는 속성이라 `is_intro` 같은 정적 컬럼이 맞았습니다.
반면 이번 주 레시피와 오늘의 미션은 기간이 지나면 다시 뽑혀야 하므로, 별도 선택 테이블이 더 적합했습니다.

즉, 이번 작업에서는

- 변하지 않는 분류는 엔티티 속성
- 날짜/주차에 따라 바뀌는 결과는 선택 테이블

로 구분했습니다.

### 2) 최초 조회 시 생성 후 재사용 흐름으로 간 점

현재 단계에서는 별도 스케줄러 없이도 정책을 만족시킬 필요가 있었습니다.
그래서 조회 시점에:

1. 오늘/이번 주 선택 데이터가 있는지 확인
2. 있으면 그대로 반환
3. 없으면 후보군에서 선택 후 저장
4. 이후 요청부터는 같은 데이터를 재사용

흐름으로 처리했습니다.

이렇게 하면 운영 복잡도를 낮추면서도 "같은 날에는 같은 결과"를 보장할 수 있습니다.

### 3) 동시 요청에서도 중복 생성이 덜 나도록 방어한 점

최초 생성 시점에는 동시에 여러 요청이 들어올 수 있습니다.
그래서 선택 테이블에는 날짜/주차 기준 유니크 제약을 두고, 저장 중 충돌이 나면 다시 기존 데이터를 읽어오는 방식으로 정리했습니다.

이 방식은 과한 락 구조를 바로 도입하지 않으면서도, 최초 편성 중복 생성 가능성을 낮추는 데 도움이 됩니다.

### 4) 조회 응답을 화면 구조에 맞게 개편한 점

기존처럼 레시피 목록이나 미션 목록을 한 배열로만 주는 방식은 백엔드 입장에서는 단순하지만, 프론트는 섹션 분류와 대표 노출 로직을 다시 가져가야 합니다.

그래서 이번에는:

- 레시피: `introRecipes`, `weeklyRecipe`, `hiddenRecipes`
- 미션: `generalMissions`, `specialMission`

형태로 응답을 분리해 프론트가 그대로 렌더링할 수 있는 구조로 맞췄습니다.

## 6. 검증 방법

이번 작업에서는 편성 생성과 조회 응답을 나눠 검증했습니다.

### 편성 생성 테스트

- 오늘의 미션 선택 데이터가 이미 있으면 기존 데이터를 재사용하는지 확인했습니다.
- 선택 데이터가 없으면 일반 3개, 특별 1개를 생성하는지 확인했습니다.
- 후보군이 부족하면 예외가 발생하는지 확인했습니다.
- 이번 주 레시피가 이미 선택되어 있으면 기존 데이터를 재사용하는지 확인했습니다.
- 주간 선택 데이터가 없으면 일반 레시피 중 1개를 선택해 저장하는지 확인했습니다.

### 조회 응답 테스트

- 미션 API가 일반 미션 목록과 특별 미션을 구분해서 반환하는지 확인했습니다.
- 레시피 API가 입문 레시피, 이번 주 레시피, 히든 레시피 섹션 구조로 반환하는지 확인했습니다.
- 기존 사용자별 완료/노출 정보가 새 응답 구조에서도 유지되는지 함께 확인했습니다.

## 7. 이번 작업으로 해결한 것

이번 작업의 핵심 성과는 랜덤 노출을 단순 조회 로직으로 두지 않고, 운영 가능한 편성 구조로 끌어올렸다는 점입니다.

- 오늘의 미션과 이번 주 레시피를 기간 단위로 고정 노출할 수 있게 됐습니다.
- 입문 레시피, 이번 주 레시피, 히든 레시피를 화면 구조에 맞게 분리할 수 있게 됐습니다.
- 미션도 일반/특별 섹션으로 나누어 프론트가 바로 소비할 수 있는 응답 구조를 갖추게 됐습니다.
- 이후 운영툴, 스케줄러, 수동 편성 기능으로 확장할 수 있는 데이터 기반을 마련했습니다.

즉, 이번 작업은 단순 랜덤 기능 추가가 아니라, `콘텐츠 노출 정책을 저장 가능한 서버 구조로 설계한 작업`이라고 정리할 수 있습니다.
