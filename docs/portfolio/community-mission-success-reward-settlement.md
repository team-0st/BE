# 공동미션 성공 보상을 요청 트랜잭션에서 분리하고 배치 정산 구조로 개선

## 1. 문제 상황

공동미션 성공 보상은 처음에 "성공 임계치를 넘긴 한 명의 요청" 안에서 미지급 완료자 전원을 한 번에 정산하는 방식으로 구현되어 있었습니다.

이 구조는 정책 자체는 맞았지만, 성공 시점에 누적 완료자가 많아질수록 다음 부담이 커질 수 있었습니다.

- 공동미션 성공 요청 1건이 긴 트랜잭션을 점유
- 공동미션 row lock을 잡은 상태에서 다수 유저 row를 순차적으로 lock
- 재료/에코잼 지급과 이력 적재가 한 요청 안에서 모두 수행

즉, 기능은 맞지만 성공 시점 요청이 "정산 작업까지 떠안는 구조"였습니다.

추가로 재료 보상 수량이 2개 이상일 때는 같은 재료 타입 목록을 반복 조회하고 있어, 작은 보상이라도 불필요한 중복 쿼리가 발생하고 있었습니다.

## 2. 왜 문제였는가

공동미션은 일반 API와 다르게 "개별 완료"와 "전체 성공"이 같은 타이밍에 엮일 수 있습니다.

특히 성공 임계치를 넘긴 순간에는

- 현재 완료자 즉시 보상
- 이미 완료했지만 아직 미지급인 이전 완료자 정산

이 동시에 필요합니다.

이를 하나의 동기 요청 안에서 모두 처리하면, 성공을 발생시킨 한 명의 요청이 다른 정산 작업까지 책임지게 됩니다.

MVP에서는 트래픽이 크지 않더라도, 이런 구조는 이후 규모가 커질 때 가장 먼저 병목이 되기 쉬운 지점입니다.

## 3. 해결 방식

이번에는 보상 지급을 두 단계로 분리했습니다.

### 적용 방식

- 성공 임계치를 넘긴 현재 요청에서는
  - 공동미션 성공 상태만 확정
  - 현재 완료자 보상만 즉시 지급
  - 성공 이벤트만 발행
- 이전 미지급 완료자 정산은 `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` 기반으로 분리
- 비동기 정산 서비스에서는 미지급 완료자를 `Top100` 단위로 끊어서 반복 처리
- 재료 보상 목록은 reward 타입별로 미리 조회해 캐시한 뒤 재사용

즉, "성공 판정은 요청 경로", "누적 정산은 비동기 배치 경로"로 역할을 분리했습니다.

## 4. 왜 이 방식을 선택했는가

### 선택 이유

- 공동미션 성공 여부는 현재 요청에서 즉시 확정되어야 사용자 경험이 자연스럽습니다.
- 반면 누적 완료자 정산까지 현재 요청이 모두 처리할 필요는 없습니다.
- `AFTER_COMMIT` 이벤트로 분리하면 성공 상태가 DB에 반영된 뒤 정산이 시작되어 정합성을 유지하기 쉽습니다.
- `Top100` 단위 배치로 처리하면 한 번에 너무 많은 row lock과 이력 적재가 몰리는 문제를 줄일 수 있습니다.
- 재료 타입 목록 캐시는 성능 개선 효과가 작아 보여도, 반복 보상 구조에서는 가장 손쉽게 제거할 수 있는 중복 쿼리였습니다.

### 고려했던 다른 방법

#### 1) 그대로 동기 처리 유지

가장 단순하지만, 성공 시점 요청이 정산 부담을 모두 떠안는 구조가 계속 남습니다.

#### 2) 외부 메시지 큐 도입

더 확장성 있는 구조지만, 현재 MVP 단계에서는 운영 복잡도가 너무 커집니다.

#### 3) 현재 완료자까지 전부 비동기 처리

이 경우 API 응답 시점에 사용자는 성공했는지 알더라도 "내 보상이 지금 지급됐는가"를 바로 알기 어렵습니다.

그래서 현재 완료자는 즉시 지급하고, backlog만 비동기 정산하는 절충안을 선택했습니다.

## 5. 구현 중 중요했던 포인트

### 1) 성공 상태와 정산 상태를 분리한 점

- `community_missions.succeeded_at`
- `community_mission_completions.rewarded_at`

두 값을 분리해, "미션은 성공했지만 어떤 완료자가 아직 미지급인지"를 구분할 수 있게 했습니다.

### 2) 현재 완료자와 backlog 정산을 다르게 처리한 점

현재 완료자는 이미 요청 트랜잭션 안에서 유저 row lock을 잡고 있으므로 즉시 보상 지급이 자연스럽습니다.

반대로 이전 완료자는 비동기 정산 서비스에서 별도로 lock을 잡아 배치 처리하도록 분리했습니다.

### 3) 재료 목록 중복 조회를 제거한 점

기존에는 `quantity`만큼 반복하며 같은 `IngredientType` 목록을 계속 조회할 수 있었습니다.

이번에는

- reward 목록에서 필요한 `IngredientType`만 추출
- 타입별 재료 목록을 한 번만 조회
- 반복 지급에서는 캐시된 목록을 재사용

구조로 바꿔 중복 쿼리를 제거했습니다.

## 6. 검증 방법

### 완료 서비스 테스트

- 목표 미달 시 완료만 저장되고 보상은 지급되지 않는지 확인
- 목표 달성 시 현재 완료자 보상과 성공 이벤트 발행이 함께 수행되는지 확인

### 정산 서비스 테스트

- 미지급 완료자 정산이 `Top100` 반복 조회 기반으로 수행되는지 확인
- 정산 후 `rewardedAt`이 반영되는지 확인
- 에코잼 이력이 완료자 수만큼 적재되는지 확인
- 재료 보상 수량이 여러 개여도 `findAllByType`이 타입별 1회만 호출되는지 확인

## 7. 이번 작업으로 해결한 것

- 공동미션 성공 시점의 보상 정산을 요청 경로에서 분리했습니다.
- 성공을 발생시킨 한 명의 요청이 전체 backlog 정산을 떠안지 않도록 구조를 개선했습니다.
- 미지급 완료자 정산을 비동기 배치로 바꿔 확장 가능성을 높였습니다.
- 재료 보상 반복 지급의 중복 조회를 제거해 작은 비효율도 함께 정리했습니다.

즉, 이번 작업은 단순히 "코드 리뷰 코멘트를 반영했다" 수준이 아니라, 공동미션 성공 보상을 도메인 정책에 맞게 유지하면서도 요청 경로의 책임을 줄이고 정산 구조를 확장 가능한 형태로 재설계한 작업이었습니다.
