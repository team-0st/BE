# 보상 추첨 로직 공통화로 중복 제거와 정책 안정성 확보

## 1. 문제 상황

서비스 안에는 확률 기반으로 보상을 선택하는 기능이 여러 군데 있었습니다.

- 가챠 보상 추첨
- 스프 제작 보상 추첨
- 스프 리롤 보상 추첨

각 기능은 도메인 정책은 달랐지만, "가중치 또는 확률에 따라 후보 중 하나를 선택한다"는 핵심 구조는 같았습니다.

초기 구현에서는 이 공통 구조가 각 서비스 안에 개별적으로 들어가 있었습니다.

- 가챠는 확률 정책을 가중치로 변환한 뒤 누적합을 직접 계산했습니다.
- 스프 기본 보상은 `roll < 5`, `roll < 15` 같은 분기문으로 직접 처리했습니다.
- 스프 리롤도 등급별로 별도의 확률 분기문을 반복해서 가지고 있었습니다.

즉, 기능은 동작했지만 확률 선택 알고리즘이 여러 군데에 흩어져 있었고, 같은 개념을 서로 다른 방식으로 표현하고 있었습니다.

## 2. 왜 문제였는가

이 문제는 단순 코드 길이 문제가 아니었습니다.

- 같은 추첨 규칙을 여러 곳에서 각각 구현하면 수정 포인트가 늘어납니다.
- 누적합 계산이나 경계값 처리 방식이 조금씩 달라질 수 있습니다.
- 새로운 확률형 기능이 생길 때마다 같은 로직을 다시 작성하게 됩니다.
- 테스트도 서비스마다 개별적으로만 검증되어, 추첨 알고리즘 자체를 독립적으로 검증하기 어렵습니다.

즉, 도메인 정책은 달라도 "후보군 중 하나를 확률적으로 선택하는 알고리즘"은 공통 개념인데, 이를 공유하지 않으면 유지보수성과 안정성이 함께 떨어질 수 있었습니다.

## 3. 해결 방식

이번에는 정책 저장 방식과 보상 적용 방식은 그대로 두고, 추첨 실행 알고리즘만 공통 컴포넌트로 추출했습니다.

### 적용 방식

- `WeightedCandidate<T>`를 추가해 추첨 후보와 가중치를 공통 표현으로 만들었습니다.
- `WeightedRandomSelector`를 추가해 가중치 합산과 누적 구간 선택을 한 곳에서 처리하도록 구성했습니다.
- 가챠는 `GachaRewardPolicy`를 `WeightedCandidate<GachaRewardPolicy>`로 변환한 뒤 공통 선택기를 사용하도록 변경했습니다.
- 스프 보상과 스프 리롤은 각 보상 후보를 `WeightedCandidate<RewardResult>` 구조로 표현하도록 정리했습니다.

즉, "정책은 각 도메인이 만들고, 선택은 공통 선택기가 수행한다"는 구조로 책임을 분리했습니다.

## 4. 왜 이 방식을 선택했는가

### 선택 이유

- 가챠와 스프는 보상 적용 방식이 달라서, 지급 로직까지 한 번에 공통화하면 범위가 과도하게 커집니다.
- 반면 확률 선택 알고리즘은 도메인과 무관하게 동일한 문제이기 때문에 먼저 분리하기 적합했습니다.
- 리팩터링 범위를 "정책 저장 통합"이 아니라 "추첨 실행 통합"으로 제한하면 기존 기능을 크게 흔들지 않고도 중복을 줄일 수 있습니다.
- 이후 공동 미션 보상, 출석 랜덤 보상 같은 기능이 추가돼도 같은 선택기를 재사용할 수 있습니다.

### 고려했던 다른 방법

#### 1) 가챠와 스프의 보상 정책까지 하나의 구조로 통합

이 방식은 이상적으로 보일 수 있지만, 현재는 가챠가 DB 정책 기반이고 스프는 코드 정책 기반이라 저장 방식과 부작용 처리까지 함께 바꾸게 됩니다.
이번 이슈의 범위로는 너무 컸습니다.

#### 2) 스프만 먼저 리팩터링

중복은 줄일 수 있지만, 가챠 쪽에 남아 있는 누적합 계산 로직은 그대로 유지됩니다.
이번에는 "확률 선택"이라는 공통 개념을 기준으로 공통화를 진행하는 편이 더 일관적이었습니다.

#### 3) 기존 if/else 분기 유지

가장 안전해 보이지만, 리롤까지 들어오면서 분기문이 많아졌고 공통 알고리즘을 추출할 타이밍이 명확해졌다고 판단했습니다.

## 5. 구현 중 중요했던 포인트

이번 공통화에서 가장 중요한 포인트는 스프 보상 후보의 지연 평가였습니다.

스프 보상은 단순 숫자만 고르는 것이 아니라, 재료 보상 후보를 만들 때 `randomCommonIngredient()`나 `randomHiddenIngredient()` 같은 추가 계산이 들어갑니다.

처음에는 보상 후보를 미리 `RewardResult`로 만들어 `WeightedCandidate<RewardResult>`에 넣으려 했습니다.
하지만 이 방식은 실제로 뽑히지 않은 후보의 재료 생성 로직까지 미리 실행될 수 있다는 문제가 있었습니다.

그래서 스프 쪽은 최종적으로 `WeightedCandidate<() -> RewardResult>` 형태로 정리했습니다.

- 후보 생성 시점에는 가중치와 "보상 생성 함수"만 준비
- 실제 선택된 후보만 마지막에 실행해 `RewardResult` 생성

이렇게 바꿔야 공통화 이후에도 기존 보상 정책의 실행 순서를 깨지지 않게 유지할 수 있었습니다.

## 6. 검증 방법

이번 작업에서는 공통 선택기 자체와 기존 도메인 회귀를 함께 검증했습니다.

### 공통 선택기 테스트

- 누적 가중치 구간에 따라 원하는 후보가 선택되는지 확인했습니다.
- 빈 후보 리스트일 때 예외가 발생하는지 확인했습니다.

### 기존 서비스 회귀 테스트

- 가챠 실행 테스트가 기존과 동일하게 통과하는지 확인했습니다.
- 스프 제작 보상 테스트가 기존과 동일하게 통과하는지 확인했습니다.
- 스프 리롤 보상 테스트가 기존과 동일하게 통과하는지 확인했습니다.

즉, "공통화는 했지만 정책 동작은 바뀌지 않았다"는 점을 테스트로 확인했습니다.

## 7. 이번 작업으로 해결한 것

이번 작업의 핵심 성과는 확률형 기능의 정책 자체를 바꾸지 않고, 중복되던 추첨 알고리즘만 안정적으로 공통화했다는 점입니다.

- 가챠와 스프에 흩어져 있던 가중치 선택 로직을 한 곳으로 모았습니다.
- 도메인별 정책 표현은 유지하면서도, 선택 알고리즘의 중복 구현을 제거했습니다.
- 공통 선택기를 독립 테스트할 수 있게 되어 추첨 알고리즘 자체의 신뢰도를 높였습니다.
- 이후 확률형 기능이 늘어나더라도 같은 컴포넌트를 재사용할 수 있는 기반을 만들었습니다.

즉, 이번 작업은 단순 코드 정리가 아니라, 기능 정책은 건드리지 않으면서도 변동성이 낮은 공통 축을 먼저 추출해 리팩터링 범위를 적절하게 통제한 작업이었습니다.
