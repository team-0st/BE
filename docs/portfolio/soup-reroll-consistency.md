# 스프 리롤 기능의 보상 교체 정합성 처리

## 1. 문제 상황

스프 제작 기능에 리롤을 추가하면서, 사용자가 이미 받은 보상을 다시 추첨해 최종 결과를 바꾸는 요구사항이 생겼습니다.

표면적으로는 "한 번 더 뽑기"처럼 보이지만, 실제로는 단순 랜덤 재실행으로 끝나는 문제가 아니었습니다.

기존 스프 제작 완료 시점에는 다음 데이터가 이미 반영되어 있었습니다.

- `soups`에 보상 등급, 에코잼, 포인트가 저장됨
- 사용자 보유 에코잼과 포인트가 증가함
- 보상 재료가 `user_ingredients`에 적재됨
- `soup_reward_ingredients`에 지급 재료 이력이 저장됨
- 에코잼/포인트/재료 이력이 함께 적재됨

즉, 리롤은 새 보상을 추가로 주는 기능이 아니라, 이미 반영된 기존 보상을 되돌린 뒤 새 최종 보상으로 교체해야 하는 기능이었습니다.

## 2. 왜 문제였는가

이 문제의 핵심은 재추첨 자체보다 정합성이었습니다.

- 기존 보상을 유지한 채 새 보상을 주면 리롤이 아니라 추가 지급이 됩니다.
- 에코잼, 포인트, 재료 중 하나라도 회수/재적용이 어긋나면 사용자 자산이 꼬일 수 있습니다.
- `soups`의 최종 보상 값과 실제 사용자 자산 상태가 달라질 수 있습니다.
- 보상 이력이 모두 적립 기준으로만 쌓이면 리롤 이후 어떤 자산이 회수되었는지 추적하기 어렵습니다.

즉, 리롤은 단순 UI 액션이 아니라 "기존 상태를 안전하게 되돌리고 새 상태로 교체하는 서버 정합성 문제"였습니다.

## 3. 해결 방식

이번에는 리롤을 다음 순서의 상태 전이로 정의했습니다.

1. 리롤 가능 여부를 검증한다.
2. 리롤 비용 에코잼을 차감한다.
3. 기존 보상을 회수한다.
4. 현재 등급 이상만 나오는 확률표로 새 보상을 다시 추첨한다.
5. 새 보상을 사용자 자산에 다시 적용한다.
6. 스프를 리롤 완료 상태로 저장한다.
7. 관련 이력을 모두 남긴다.

### 적용 방식

- `soups` 테이블에 `rerolled` 컬럼을 추가해 제작당 1회 제한을 서버에서 보장했습니다.
- `SoupRerollService`를 별도로 두어 리롤 비용 차감, 리롤 가능 여부 검증, 1회 제한 검증을 담당하게 했습니다.
- `SoupRewardService`에 `reroll(...)` 흐름을 추가해 기존 보상 회수와 새 보상 재적용을 한 곳에서 처리했습니다.
- 기존 지급 재료는 `soup_reward_ingredients`를 기준으로 조회해 회수한 뒤, 새 보상 재료로 다시 저장하도록 구성했습니다.
- `IngredientHistory`, `PointHistory`에 음수 이력을 남길 수 있도록 `spend(...)` 팩토리를 추가했습니다.
- 에코잼, 포인트, 재료 이력 source에 `SOUP_REROLL` 타입을 추가해 리롤 비용 차감과 기존 보상 회수를 구분 가능하게 했습니다.

## 4. 왜 이 방식을 선택했는가

### 선택 이유

- 리롤은 독립 기능처럼 보이지만 실제로는 기존 스프 보상의 후속 상태 변화이기 때문에, `Soup` 하나를 기준으로 상태를 관리하는 편이 자연스럽습니다.
- 기존 보상 회수 기준은 이미 저장된 `Soup.rewardEcoJam`, `Soup.rewardPoint`, `SoupRewardIngredient`이므로, 별도 계산보다 저장된 결과를 기준으로 되돌리는 방식이 더 안전합니다.
- 사용자 자산과 보상 이력이 항상 함께 움직이도록 묶어야 이후 운영 중 문제 원인을 추적하기 쉽습니다.
- 리롤 정책은 `SoupRerollService`, 자산 교체 정합성은 `SoupRewardService`로 분리해 역할을 나누면 이후 보상 공통화 리팩터링에도 유리합니다.

### 고려했던 다른 방법

#### 1) 기존 보상 유지 후 새 보상 추가 지급

구현은 단순하지만, 리롤의 의미가 "최종 보상 교체"가 아니라 "추가 보상 지급"으로 바뀌어 버립니다.
보상 인플레이션이 생기고 정책 의도와도 맞지 않았습니다.

#### 2) 새 스프를 다시 생성하는 방식

리롤은 기존 제작 결과를 바꾸는 기능인데, 새 `Soup` row를 생성하면 제작 이력과 리롤 이력이 섞이게 됩니다.
제작당 1회 제한도 더 복잡해집니다.

#### 3) 차액만 계산해 반영

최종 자산만 맞추는 데는 도움이 되지만, 기존 보상이 무엇이었고 무엇을 회수했는지 추적성이 떨어집니다.
특히 재료 보상은 차액 기반보다 실제 지급분을 기준으로 회수하는 편이 더 명확했습니다.

## 5. 함께 해결한 정책 문제

리롤은 확률 재추첨만 추가하는 기능이 아니라, 정책 제약이 함께 들어가는 기능이었습니다.

이번 구현에서는 다음 규칙을 함께 반영했습니다.

- 제작당 리롤은 1회만 가능
- 최고 등급(`JACKPOT`)은 리롤 불가
- 현재 보상보다 낮은 등급은 나오지 않도록 확률표 분리
- 스프 타입과 현재 등급에 따라 리롤 비용 차등 적용

예를 들어 일반 스프는 `CONSOLATION -> 30`, `INGREDIENT -> 50`, `SMALL -> 70`, `MIDDLE -> 100`으로 구성했고,
히든/전설 스프는 더 높은 비용 정책을 적용했습니다.

즉, 리롤은 단순 랜덤 호출이 아니라 "정책 기반 상태 전이"로 설계되었습니다.

## 6. 검증 방법

이번 작업에서는 단순 성공 응답만 확인하지 않고, 실제 자산 상태와 이력 흐름이 맞는지 테스트로 검증했습니다.

테스트 시나리오는 다음과 같습니다.

- 일반 스프 꽝 보상을 리롤할 때 리롤 비용이 차감되고, 기존 보상이 회수된 뒤 새 보상이 적용되는가
- 재료 보상을 리롤할 때 기존 지급 재료가 회수되고 새 재료 보상이 다시 적재되는가
- 이미 리롤한 스프는 다시 리롤할 수 없는가
- 컨트롤러에서 리롤 응답 구조가 의도대로 반환되는가
- 기존 스프 제작 테스트가 리롤 구조 추가 후에도 깨지지 않는가

즉, 리롤 테스트는 단순 기능 테스트가 아니라, 자산 정합성 회귀 테스트 성격도 함께 가졌습니다.

## 7. 이번 작업으로 해결한 것

이번 작업의 핵심 성과는 스프 리롤을 "추가 보상"이 아니라 "최종 보상 교체"로 안전하게 구현했다는 점입니다.

- 에코잼, 포인트, 재료를 함께 다루는 보상 교체 정합성을 확보했습니다.
- 리롤 비용 차감, 기존 보상 회수, 새 보상 재적용이 한 흐름으로 연결되도록 정리했습니다.
- 적립만 존재하던 이력 구조를 사용/회수까지 표현 가능하도록 확장했습니다.
- 리롤 1회 제한, 최고 등급 제외, 하위 등급 금지 같은 정책을 서버에서 강제했습니다.

즉, 이번 작업은 단순한 "재추첨 API 추가"가 아니라, 여러 자산이 동시에 변하는 게임성 기능에서 상태 일관성과 추적 가능성을 함께 보장하도록 구조를 보완한 작업이었습니다.
