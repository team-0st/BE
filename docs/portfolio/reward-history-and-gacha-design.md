# 재화 이력 추적 구조와 가챠 정합성 문제 해결

## 1. 문제 상황

서비스에 에코잼, 포인트, 재료처럼 사용자의 자산이 계속 변하는 기능이 늘어나기 시작했습니다.

초기 구조에서는 `users.eco_jam`, `users.point`처럼 현재 잔액만 저장하면 기능 자체는 동작할 수 있었습니다.

하지만 이 방식만으로는 다음 질문에 답하기 어려웠습니다.

- 왜 잔액이 지금 값이 되었는가
- 어떤 기능이 얼마를 적립하거나 차감했는가
- 운영 중 잘못된 지급이나 중복 지급이 발생했는가

특히 스프 보상과 가챠처럼 "재화 차감 또는 적립"이 함께 일어나는 기능은 현재 잔액만으로는 추적성이 부족했습니다.

## 2. 왜 문제였는가

이 문제는 단순 로그 부재가 아니라, 운영성과 정합성 문제였습니다.

- 사용자 문의가 들어와도 재화 변동 근거를 설명하기 어렵습니다.
- 잘못된 적립이나 중복 차감이 생겨도 원인 추적이 어렵습니다.
- 가챠처럼 확률형 기능은 결과와 차감 이력이 함께 남아야 운영 검증이 가능합니다.

즉, 재화 시스템은 "현재 얼마를 가지고 있는가"만 관리해서는 부족했고, "왜 그렇게 되었는가"까지 남기는 구조가 필요했습니다.

## 3. 해결 방식

이번에는 현재 잔액과 변동 이력을 분리하는 구조로 문제를 해결했습니다.

### 적용 방식

- `users`에는 현재 잔액인 `eco_jam`, `point`를 유지했습니다.
- 별도로 `eco_jam_histories`, `point_histories` 테이블을 추가했습니다.
- 이력에는 `amount`, `source_type`, `source_id`를 저장하도록 설계했습니다.
- 스프 보상 지급 시 잔액 증가와 이력 저장이 같은 트랜잭션 안에서 함께 일어나도록 연결했습니다.
- 이후 이력 조회 API를 추가해 사용자 기준 최신순 내역 조회가 가능하도록 구성했습니다.

즉, 현재 상태와 변동 근거를 분리하되, 둘이 항상 함께 움직이도록 트랜잭션 경계를 맞췄습니다.

## 4. 왜 이 방식을 선택했는가

### 선택 이유

- 현재 잔액 조회는 빠르게 유지할 수 있습니다.
- 운영/정산/문의 대응 시 변동 근거를 별도 이력에서 확인할 수 있습니다.
- `source_type`, `source_id`를 기준으로 어떤 기능에서 발생한 변화인지 추적할 수 있습니다.
- 이후 미션, 출석, 가챠처럼 다른 적립/차감 소스도 같은 구조로 확장할 수 있습니다.

### 고려했던 다른 방법

#### 1) 잔액 컬럼만 유지

구현은 가장 단순하지만, 변동 원인과 실행 맥락을 잃게 됩니다.

#### 2) 모든 조회를 이벤트성 로그에만 의존

정산이나 추적에는 유리할 수 있지만, 현재 잔액 조회가 매번 비싸지고 애플리케이션 구조도 더 복잡해집니다.

#### 3) 재화별 통합 테이블 하나로 저장

확장성은 있어 보이지만, 현재 단계에서는 에코잼과 포인트의 정책과 조회 요구가 다를 수 있어 분리형이 더 명확하다고 판단했습니다.

## 5. 가챠에서 함께 해결한 정합성 문제

가챠는 재화 정합성이 가장 민감한 기능이었습니다.

가챠 1회 실행은 다음 흐름을 가집니다.

1. 에코잼을 차감한다.
2. 확률에 따라 보상을 결정한다.
3. 포인트, 에코잼, 재료 중 하나를 지급한다.
4. 가챠 실행 결과와 재화 이력을 저장한다.

이 흐름에서 핵심은 "랜덤 결과가 무엇인가"보다 "차감과 지급이 항상 함께 맞는가"였습니다.

### 적용한 방식

- 가챠 실행 시작 시 `UserRepository.findByDeviceIdForUpdate(...)`로 사용자 row를 `PESSIMISTIC_WRITE`로 조회했습니다.
- 에코잼 부족 여부를 먼저 검증한 뒤 차감하도록 구성했습니다.
- 가챠 확률은 코드 하드코딩 대신 `gacha_reward_policies` 테이블에서 읽도록 설계했습니다.
- 실제 실행 결과는 `gachas` 테이블에 남기고, 그 결과를 기준으로 재화 이력을 적재하도록 구성했습니다.

## 6. 왜 가챠 정책을 DB로 분리했는가

가챠 확률과 보상 정책은 운영상 민감한 정보였습니다.

- 퍼블릭 레포에 확률을 그대로 노출하고 싶지 않았습니다.
- 파일럿 운영 중 확률 조정이 필요할 수 있었습니다.
- 코드 배포 없이 정책만 수정할 수 있는 여지를 남기고 싶었습니다.

그래서 Flyway에는 테이블만 생성하고, 실제 확률 데이터는 배포 후 직접 입력하는 구조로 정리했습니다.

이 방식으로 "코드는 실행 구조", "DB는 운영 정책"이라는 책임을 분리할 수 있었습니다.

## 7. 검증 방법

이번 작업에서는 기능 동작뿐 아니라 재화 흐름이 올바르게 이어지는지 테스트로 확인했습니다.

가챠 서비스 테스트에서는 다음을 검증했습니다.

- 에코잼이 부족하면 실행되지 않는가
- 포인트 보상 시 에코잼 차감 후 포인트가 적립되는가
- 에코잼 보상 시 사용 이력과 적립 이력이 함께 남는가
- 재료 보상 시 `user_ingredients`가 정상 증가하는가

이력 조회 테스트에서는 다음을 검증했습니다.

- 에코잼/포인트 이력이 최신순으로 조회되는가
- 같은 시각 데이터가 있을 때 `createdAt desc, id desc` 기준이 유지되는가
- 미등록 유저는 조회할 수 없는가

## 8. 이번 작업으로 해결한 것

이번 작업의 핵심 성과는 재화를 단순 숫자로 다루지 않고, 운영 가능한 자산 시스템으로 정리했다는 점입니다.

- 현재 잔액과 변동 근거를 분리해 추적 가능성을 확보했습니다.
- 스프 보상과 가챠 실행 모두에서 재화 정합성을 트랜잭션 단위로 관리하도록 구성했습니다.
- 가챠 확률 정책을 코드에서 분리해 운영 변경 가능성과 정보 은닉성을 함께 고려했습니다.
- 이후 미션, 출석, 가챠 확장에서도 같은 이력 구조를 재사용할 수 있는 기반을 만들었습니다.

즉, 이번 작업은 단순 기능 추가가 아니라, 재화가 계속 누적되고 소비되는 서비스에서 필요한 정합성, 추적성, 운영 확장성 문제를 함께 해결한 작업이었습니다.
