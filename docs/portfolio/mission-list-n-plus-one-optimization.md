# 미션 목록 조회 N+1을 측정 가능한 개선 작업으로 정리한 기록

## 1. 문제를 어떻게 바라봤는가

`GET /api/v1/missions`는 단순한 목록 조회처럼 보이지만, 실제로는 다음 정보를 한 번에 계산합니다.

- 오늘 편성된 일반 미션 3개
- 오늘 편성된 특별 미션 1개
- 각 미션의 오늘 제출 상태
- 보상 수령 가능 여부
- 보상 수령 완료 여부

즉, "목록 조회" 안에 상태 계산이 함께 들어 있는 API였습니다.

이 구조에서 먼저 확인한 부분은  
`오늘 편성된 미션 개수만큼 completion 조회가 반복되는 N+1 패턴`이었습니다.

이번 작업은 바로 최적화 코드를 넣기보다,

1. 실제로 SQL이 몇 번 나가는지
2. 단건 호출 시간은 어느 정도인지
3. 동시 요청이 들어오면 응답 시간이 어떻게 변하는지

를 먼저 수치로 고정한 뒤, 같은 시나리오로 개선 후를 다시 비교하는 방식으로 진행했습니다.

## 2. 측정 기준

측정은 두 층으로 나눴습니다.

### 1) 로컬 측정

- `MissionQueryServiceTest`
  - 기능 회귀 여부 확인
- `MissionQueryServiceMeasurementTest`
  - SQL 실행 수
  - 첫 호출 시간
  - 반복 호출 평균 / 최소 / 최대 시간

### 2) k6 부하테스트

같은 API를 다음 시나리오로 반복 호출했습니다.

- `1 VU`
- `10 VU`
- `30 VU`
- `50 VU`
- `100 VU spike`
- `200 VU spike`

낮은 부하 구간은 `1 / 10 / 30 VU` 3회, `50 VU` 2회로 측정했고,
짧은 스파이크 구간은 `100 VU` 3회, `200 VU` 2회로 측정했습니다.

## 4. 어떤 방식으로 개선했는가

선택지는 여러 가지가 있었습니다.

- `fetch join`
- DTO projection + 서브쿼리
- 캐시 적용
- 오늘 상태를 별도 스냅샷으로 저장

하지만 이번에는  
`오늘 편성된 미션 ID 목록을 먼저 모으고, completion을 한 번에 조회한 뒤, missionId 기준으로 매핑하는 배치 조회 방식`을 선택했습니다.

이 문서에서는 이 방식을 기준으로 정리했습니다.

### 1) 변경 범위가 작았습니다

응답 구조를 바꾸지 않고,

- 오늘 편성 미션 ID 수집
- completion 일괄 조회
- 서비스 내부 매핑

정도로 바꿀 수 있었습니다.

### 2) "오늘의 최신 제출 1건" 의미를 유지하기 쉬웠습니다

`MissionCompletion`은 미션당 한 건만 있는 구조가 아니기 때문에,
단순 fetch join으로는 "오늘 상태로 어떤 completion을 보여줄지"를 다루기 까다로웠습니다.

반면 이번 방식은

- 오늘 범위 조건으로 모아서 조회하고
- `missionId`별로 묶은 뒤
- 정렬된 결과의 첫 번째를 사용

하는 식으로 기존 의미를 자연스럽게 유지할 수 있었습니다.

### 3) 비교 지점을 나누기 쉬웠습니다

- 기존: 미션별 개별 조회
- 변경: 오늘 미션 대상 일괄 조회

로 나눌 수 있어서 비교 포인트가 분명했습니다.

### 4) 캐시보다 조회 구조를 먼저 정리했습니다

캐시는 반복 조회를 줄일 수는 있지만, N+1 구조 자체를 없애지는 않습니다.
이번에는 캐시를 붙이기 전에 조회 흐름부터 정리했습니다.

## 7. 결과 해석

이번 결과에서는 쿼리 구조 변화와 응답 시간 변화가 같은 폭으로 움직이지 않았습니다.

### 1) SQL 수는 줄었습니다

- 개선 전: `7`
- 개선 후: `4`

즉, 미션별로 반복되던 상태 조회를 일괄 조회로 바꾸면서
목록 1회 조회에 필요한 round-trip 수를 줄였습니다.

### 2) 낮은 부하 구간에서는 응답 시간 차이가 크지 않았습니다

`1 / 10 / 30 / 50 VU` 구간에서는 일부 수치가 좋아졌고, 일부는 비슷하거나 소폭 나빠졌습니다.

- 오늘 편성 미션 수가 4개로 작고
- 테스트 데이터 자체가 작고
- 네트워크, JVM warmup, dev 환경 편차가 전체 시간에 더 크게 섞이기 때문입니다.

즉, 이 구간에서는 SQL 3개 감소가 즉시 큰 latency 차이로 나타나기 어렵습니다.

### 3) 스파이크 구간에서는 `100 VU` 비교가 더 단순했습니다

`100 VU`에서는 개선 후 수치가 조금 더 낮게 나왔습니다.

- avg: `221.46ms → 216.14ms`
- p95: `375.85ms → 341.49ms`
- req/s: `36.34 → 36.88`

반면 `200 VU`는 개선 후가 더 좋아졌다고 단정하기 어려웠습니다.
두 번의 실행 결과가 같은 방향으로 모이지 않았기 때문에 dev 환경 편차도 함께 봐야 했습니다.

그래서 문서에서는

- `100 VU`: 구조 변화가 수치에 조금 드러난 구간
- `200 VU`: 환경 편차 영향도 함께 보는 구간

으로 나눠 두었습니다.

## 8. 정리

이번 작업의 핵심은 "응답 시간이 크게 줄었다"보다, 조회 구조를 측정 가능한 방식으로 바꿨다는 점에 있습니다.

이번 작업에서 남은 내용은 세 가지입니다.

- 개선 전후를 같은 테스트와 같은 부하 시나리오로 비교할 수 있게 했습니다.
- N+1 문제를 SQL 수 기준으로 확인할 수 있게 했습니다.
- 응답 시간이 크게 달라지지 않은 구간도 그대로 남겼습니다.

이번 작업은  
`자주 호출되는 조회 API의 N+1을 줄이고, 그 결과를 SQL 수와 부하테스트 기준으로 함께 비교할 수 있게 만든 작업`으로 정리할 수 있습니다.
