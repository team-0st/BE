# 관리자 미션 검수 동시성 정합성 보완

## 1. 문제 상황

관리자 미션 검수 API는 같은 미션 인증 제출 건을 `APPROVED` 또는 `REJECTED`로 변경하는 기능입니다.

초기 구현은 다음 순서로 동작했습니다.

1. 미션 인증 제출 건을 조회한다.
2. 현재 상태가 `PENDING`인지 확인한다.
3. `APPROVED`이면 보상 재료를 지급한다.
4. 검수 상태와 `reviewedAt`을 저장한다.

이 구조는 단일 요청에서는 자연스럽게 보이지만, 같은 `completionId`를 두 명의 관리자가 거의 동시에 승인하면 두 요청 모두 `PENDING` 상태를 기준으로 로직을 시작할 수 있습니다.

그 결과 다음 문제가 생길 수 있었습니다.

- 같은 미션 인증 제출 건이 중복 승인될 수 있습니다.
- 같은 보상 재료가 중복 지급될 수 있습니다.
- `user_ingredients` 수량 증가가 동시 요청에서 꼬일 수 있습니다.

즉, 관리자 검수는 단순 상태 변경이 아니라 보상 지급까지 포함된 정합성 문제였습니다.

## 2. 왜 문제였는가

이 문제는 운영자 실수 한 번으로 끝나는 문제가 아니라, 같은 데이터에 대한 동시 수정이 보상 지급과 바로 연결된다는 점이 핵심이었습니다.

- 검수 상태가 한 번만 바뀌어야 하는데 여러 번 바뀔 수 있습니다.
- 같은 사용자에게 같은 보상이 중복 적재될 수 있습니다.
- `user_ingredients`의 `(user_id, ingredient_id)` 유니크 제약과 충돌하거나 수량 반영이 누락될 수 있습니다.

즉, "이미 검수된 건은 다시 검수할 수 없다"는 규칙과 "승인 시 보상은 한 번만 지급된다"는 규칙을 함께 보장해야 했습니다.

## 3. 선택한 해결 방식

이번에는 검수 대상과 사용자 재료 갱신 지점을 각각 비관적 락으로 직렬화하는 방식으로 정리했습니다.

### 적용 방식

- `MissionCompletionRepository.findByIdForUpdate(...)`를 추가해 검수 대상 row를 `PESSIMISTIC_WRITE`로 조회했습니다.
- 같은 `completionId`에 대한 동시 승인 요청은 첫 번째 트랜잭션이 끝날 때까지 대기하도록 구성했습니다.
- 보상 지급 전에 `UserRepository.findByIdForUpdate(...)`로 사용자 row도 `PESSIMISTIC_WRITE`로 조회했습니다.
- 같은 사용자에 대한 보상 수량 갱신도 직렬화되도록 구성했습니다.
- `reward_ingredient_pool`은 잘못된 값이 섞여 있어도 조용히 무시하지 않고, 즉시 예외를 반환하도록 엄격 파싱으로 변경했습니다.

## 4. 왜 이 방식을 선택했는가

### 선택 이유

- 검수 상태 변경의 기준은 `mission_completions` row 하나이기 때문에 락 대상이 명확합니다.
- 보상 적재의 기준은 같은 사용자 재고이기 때문에 사용자 row 직렬화로 수량 갱신 충돌 범위를 줄일 수 있습니다.
- 별도 분산 락이나 DB 전용 upsert에 비해 현재 구조에서 의도가 더 잘 드러납니다.
- 운영성 기능이기 때문에 "성공 1회, 이후 요청은 실패" 규칙을 트랜잭션 레벨에서 직접 보장하기 좋습니다.

### 고려했던 다른 방법

#### 1) 상태 확인 후 저장만 유지

가장 단순하지만, 동시 승인 상황에서 중복 보상 지급을 막지 못합니다.

#### 2) `user_ingredients` upsert만 적용

수량 갱신 자체는 안전하게 만들 수 있지만, 같은 미션 인증 제출 건의 중복 승인까지 설명하기 어렵습니다.
이번 문제는 재고 증가뿐 아니라 검수 상태 전이도 함께 보장해야 했습니다.

#### 3) 분산 락 적용

Redis 같은 외부 락도 가능하지만, 현재 규모에서는 DB 트랜잭션과 row lock으로 충분히 해결 가능한 범위라고 판단했습니다.

## 5. 함께 보완한 부분

이번 작업에서는 동시성 외에도 운영 중 장애를 늦게 발견하지 않도록 설정 검증을 강화했습니다.

- `MissionCompletionRepository`의 `@EntityGraph` 경로를 `missions`가 아니라 실제 필드명인 `mission`으로 수정했습니다.
- `reward_ingredient_pool` 파싱 시 `"[1, invalid]"` 같은 잘못된 값을 조용히 무시하지 않고 `INVALID_MISSION_REWARD_POOL` 예외로 처리했습니다.
- DB `json` 컬럼을 거쳐 문자열에 따옴표가 감싸진 경우도 파싱 가능하도록 보정했습니다.

## 6. 검증 방법

`AdminMissionReviewConcurrencyTest`를 추가해 실제 동시 승인 상황을 재현했습니다.

테스트 시나리오는 다음과 같습니다.

1. 하나의 `PENDING` 미션 인증 제출 건을 준비합니다.
2. 같은 `completionId`에 대해 스레드 2개가 동시에 `APPROVED` 처리를 시도합니다.
3. 결과를 수집해 성공/실패 개수와 최종 보상 적재 상태를 검증합니다.

기대 결과는 다음과 같습니다.

- 성공 1건
- 실패 1건
- 실패 원인은 `INVALID_MISSION_REVIEW_STATUS`
- 최종 검수 상태는 `APPROVED`
- `user_ingredients` 수량은 1개만 증가

## 7. 이번 작업으로 증명한 것

이번 테스트가 증명한 것은 응답 속도 개선이 아니라, 운영자 동시 작업 상황에서도 검수 상태와 보상 지급 정합성이 깨지지 않는다는 점입니다.

즉, 이번 작업의 핵심 성과는 다음입니다.

- 같은 미션 인증 제출 건의 중복 승인 방지
- 승인 보상의 중복 지급 방지
- 사용자 보유 재료 수량 갱신의 일관성 보장
- 잘못된 미션 보상 설정을 조기에 감지하는 방어 로직 추가

이번 보완을 통해 관리자 미션 검수 API는 단순 상태 변경 API를 넘어, 운영 액션과 보상 적재가 함께 일어나는 흐름에서도 비즈니스 규칙을 일관되게 지키도록 정리되었습니다.
