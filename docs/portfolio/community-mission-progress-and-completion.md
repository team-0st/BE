# 공동미션을 전체 유저 대비 달성 비율 기반으로 설계하고 완료 구조까지 연결

## 1. 문제 상황

공동미션은 개인 미션과 달리 "한 사용자가 완료했는가"만으로 끝나지 않는 기능이었습니다.

핵심은 다음 두 가지였습니다.

- 전체 유저 중 얼마나 많은 사용자가 참여했는가
- 그 비율이 운영에서 정한 목표치에 도달했는가

즉, 공동미션은 단순 CRUD가 아니라 `전체 유저 대비 진행률 계산`, `성공 여부 판정`, `단계 해금`, `개별 완료 저장`이 함께 맞물리는 구조였습니다.

초기에는 아직 공동미션 전용 구조가 없었기 때문에, 다음 문제를 먼저 풀어야 했습니다.

- 공동미션을 기존 개인 미션과 같은 테이블/흐름으로 볼 수 있는가
- 목표 달성 기준을 고정 인원 수가 아니라 비율 기준으로 어떻게 설계할 것인가
- 운영 중 바뀔 수 있는 목표 퍼센트를 코드가 아니라 어디에서 관리할 것인가
- 사용자 완료 데이터가 진행률 집계와 어떻게 연결되어야 하는가

## 2. 왜 문제였는가

공동미션은 개인 미션을 조금 변형한 수준이 아니었습니다.

- 개인 미션은 사용자 1명의 제출과 검수 결과가 중요합니다.
- 공동미션은 여러 사용자의 완료가 누적되어 하나의 진행률을 만듭니다.
- 같은 사용자의 완료 여부는 진행률 집계와 단계 해금 조건에도 직접 영향을 줍니다.

즉, 공동미션은 "개별 상태"와 "전체 집계 상태"를 함께 다뤄야 했습니다.

이때 구조를 잘못 잡으면 다음 문제가 생길 수 있었습니다.

- 목표 인원이 고정값이면 사용자 수가 바뀔 때 난이도가 급격히 흔들릴 수 있습니다.
- 목표 퍼센트가 코드에 박혀 있으면 운영 중 정책 변경 때마다 배포가 필요합니다.
- 단계 해금 조건이 조회와 완료 처리에서 다르게 계산되면 사용자 경험이 꼬일 수 있습니다.
- 완료 저장과 집계 기준이 어긋나면 진행률이 실제보다 부풀려질 수 있습니다.

## 3. 해결 방식

이번에는 공동미션을 기존 `missions`와 분리된 별도 도메인으로 설계했습니다.

### 적용 방식

- `community_missions` 테이블을 추가해 공동미션 마스터를 분리했습니다.
- `difficulty`, `stage`, `target_ratio`, `is_active` 컬럼을 두어 난이도와 단계, 목표 퍼센트, 활성 상태를 관리하도록 구성했습니다.
- `community_mission_completions` 테이블을 추가해 사용자별 완료 이력을 저장하도록 했습니다.
- 진행률은 `완료 유저 수 / 온보딩 완료 유저 수 * 100` 기준으로 계산했습니다.
- 성공 여부는 반올림된 응답값이 아니라 더 높은 정밀도의 내부 계산값으로 판정했습니다.
- 단계 해금 조건은 `같은 난이도 내 이전 stage 완료 여부`로 통일했습니다.
- 완료 처리 API에서는 `온보딩 완료 여부`, `해금 여부`, `중복 완료 여부`를 검증한 뒤 완료 이력을 저장하도록 구성했습니다.

즉, 공동미션은 "운영 정책은 마스터 테이블", "사용자 완료는 완료 이력 테이블", "진행률/성공 여부는 조회 시 계산" 구조로 책임을 나눴습니다.

## 4. 왜 이 방식을 선택했는가

### 선택 이유

- 고정 인원 수보다 전체 유저 대비 비율 기준이 사용자 수 변화에 더 유연했습니다.
- 목표 퍼센트는 운영 중 자주 바뀔 수 있어 DB에서 관리하는 편이 맞았습니다.
- 현재 단계에서는 별도 스냅샷 적재보다 조회 시 계산 방식이 단순하고 정책 반영이 즉시 가능했습니다.
- 단계 해금 기준은 조회와 완료 저장이 같은 규칙을 써야 해서 공통 정책 객체로 분리하는 편이 안전했습니다.
- 공동미션 완료는 개인 미션처럼 검수 흐름을 바로 붙이기보다, 우선 완료 저장과 집계 연결을 먼저 닫는 것이 범위 관리에 유리했습니다.

### 고려했던 다른 방법

#### 1) 기존 `missions` 확장

처음엔 기존 미션 구조에 공동미션 속성을 얹는 방법도 생각할 수 있었습니다.
하지만 개인 미션은 제출/검수 중심이고, 공동미션은 누적 집계와 단계 해금이 핵심이라 책임이 달랐습니다.
같은 테이블에 섞으면 이후 확장 시 오히려 더 복잡해질 가능성이 컸습니다.

#### 2) 목표 인원 수 고정 방식

예를 들어 "100명 달성 시 성공"처럼 고정 인원으로도 구현은 가능합니다.
하지만 파일럿과 정식 운영에서 사용자 수가 달라질 수 있기 때문에, 사용자 수 변화에 따라 난이도가 자연스럽게 조정되는 비율 방식이 더 적합했습니다.

#### 3) 진행률 스냅샷 적재

진행률을 미리 저장해두면 조회는 빨라질 수 있습니다.
다만 현재 단계에서는 정책이 아직 바뀔 가능성이 크고, 스냅샷 동기화 비용까지 가져가는 것은 오버엔지니어링에 가까웠습니다.
그래서 우선은 조회 시 계산으로 두고, 규모가 커질 때 캐시나 스냅샷을 검토하는 쪽이 낫다고 판단했습니다.

#### 4) 참여 시작 API와 완료 API를 둘 다 먼저 도입

공동미션에는 "참여"와 "완료"를 분리할 수도 있습니다.
하지만 이번 단계에서 더 중요한 것은 진행률 집계에 반영되는 실제 완료 데이터였기 때문에, 우선 완료 저장 구조를 먼저 닫고 참여 시작 상태는 다음 확장 포인트로 남겨두었습니다.

## 5. 구현 중 중요했던 포인트

### 1) 분자/분모 기준을 일치시킨 점

진행률 분모는 `온보딩 완료 유저 수`를 기준으로 잡았습니다.
그러면 분자도 같은 기준을 써야 했습니다.

그래서 공동미션 완료 수 집계 쿼리에서도 `onboardingCompleted = true` 유저만 포함하도록 맞췄습니다.
이 기준이 어긋나면 실제보다 달성률이 부풀려질 수 있기 때문입니다.

### 2) 성공 여부는 반올림 전 값으로 판정한 점

응답에는 `42.86%`처럼 보기 좋은 값이 필요합니다.
하지만 성공 여부까지 이 반올림 값으로 판정하면 경계값에서 오차가 생길 수 있습니다.

예를 들어 `1 / 6`은 실제로는 `16.666...%`인데, 반올림하면 `16.67%`가 됩니다.
이 값을 그대로 비교하면 아직 성공이 아닌데 성공으로 보일 수 있습니다.

그래서 이번에는:

- 응답용 비율은 소수 둘째 자리 반올림
- 성공 판정은 더 높은 정밀도의 내부 계산값 사용

으로 역할을 분리했습니다.

### 3) 단계 해금 규칙을 공통 정책으로 분리한 점

공동미션은 조회할 때도 "지금 이 미션이 해금되어 있는가"를 알아야 하고,
완료 처리할 때도 "잠긴 미션을 완료할 수 없는가"를 막아야 했습니다.

이 규칙이 서비스마다 따로 구현되면 나중에 쉽게 어긋납니다.

그래서 `CommunityMissionUnlockPolicy`로 분리해:

- 조회 서비스
- 완료 저장 서비스

가 같은 기준을 쓰도록 정리했습니다.

### 4) 잘못된 운영 데이터가 들어오지 않도록 DB 제약을 둔 점

공동미션은 운영 정책성 데이터가 많아서, 애플리케이션 로직만으로 막는 것보다 DB에서도 한 번 더 방어하는 편이 안전했습니다.

그래서 다음 제약을 추가했습니다.

- `stage >= 1`
- `target_ratio >= 0 and target_ratio <= 100`
- `unique(difficulty, stage)`

이렇게 해두면 영원히 해금되지 않거나, 항상 성공해버리거나, 같은 난이도/단계가 중복되는 잘못된 데이터 입력을 줄일 수 있습니다.

## 6. 검증 방법

이번 작업에서는 진행률 조회와 완료 저장을 각각 나눠 검증했습니다.

### 진행률 조회 테스트

- 완료 유저 수와 전체 유저 수를 기준으로 달성률이 계산되는지 확인했습니다.
- 온보딩 완료 유저가 없을 때 `0.00`으로 처리되는지 확인했습니다.
- 반올림된 응답값과 별개로, 성공 여부는 반올림 전 기준으로 판정되는지 확인했습니다.
- 이전 단계 미완료 시 다음 단계가 잠금 상태로 내려오는지 확인했습니다.
- 현재 유저 완료 여부가 응답에 함께 포함되는지 확인했습니다.

### 완료 저장 테스트

- 온보딩 완료 유저는 해금된 공동미션을 완료 처리할 수 있는지 확인했습니다.
- 온보딩 미완료 유저는 완료할 수 없는지 확인했습니다.
- 잠긴 단계의 공동미션은 완료할 수 없는지 확인했습니다.
- 이미 완료한 공동미션은 중복 완료할 수 없는지 확인했습니다.

### 컨트롤러 테스트

- 공동미션 목록 조회 API 응답 형식을 확인했습니다.
- 공동미션 완료 API가 정상 응답을 반환하는지 확인했습니다.

## 7. 이번 작업으로 해결한 것

이번 작업의 핵심 성과는 공동미션을 단순 목록 기능이 아니라, 운영 정책과 사용자 완료 데이터가 함께 연결되는 도메인으로 설계했다는 점입니다.

- 공동미션을 개인 미션과 분리된 별도 도메인으로 정리했습니다.
- 목표 퍼센트를 DB 정책으로 분리해 운영 변경에 유연하게 대응할 수 있도록 했습니다.
- 진행률 계산, 성공 판정, 단계 해금, 완료 저장이 하나의 일관된 규칙 위에서 동작하도록 맞췄습니다.
- 완료 저장 구조를 추가해 이제 공동미션이 실제 사용자 행동과 집계 결과를 연결할 수 있게 되었습니다.

즉, 이번 작업은 단순 API 추가가 아니라, "전체 유저 기반 공동 목표"라는 기획 의도를 서비스 구조로 구체화하고, 이후 검수/보상 지급/운영 정책 변경까지 감당할 수 있는 기반을 마련한 작업이었습니다.
